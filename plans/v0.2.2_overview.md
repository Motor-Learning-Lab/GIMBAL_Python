# GIMBAL v0.2.2 Overview

**Purpose:** This document specifies the v0.2.2 concrete, parallelizable subprojects with clear interfaces (“contracts”), deliverables, and success criteria. It is written for a small programming team working collaboratively in a single lab GitHub repo.

**Guiding principles for v0.2.2**

* **Use data-driven priors before adding complexity.** Prioritize Anipose-derived camera/3D information and subject metadata.
* **Stabilization and reproducibility over feature growth.** The core architecture from v0.2.1 stands; v0.2.2 is about creating a ladder of datasets of increasing complexity to challenge the sampling algorithm and a number of approaches we think will make the sampling more stable.
* **Explicit contracts between modules.** Interaction between anipose, data-driven priors, datasets, and sampling algorithms needs to be well defined to enable modular development.
* **Diagnostics are the arbiter.** Current limiting capability is the sampling. All of the projects are designed to reach stable sampling on complex datasets. Every major change should show measurable improvement on the capability ladder.

## P0. Module Reorganization into Domain Subpackages (✅ Complete)

### Goal

Restructure the flat `gimbal_pymc/` package into 6 domain-specific subpackages to improve code organization, discoverability, and maintainability.

### Final Structure (Implemented)

```
gimbal_pymc/
├── hmm/                    # Hidden Markov Model components
├── cameras/                # Multi-view geometry (projection, triangulation, placement)
├── skeleton/               # Body structure, motion, metrics, visualization
├── joints/                 # Directional statistics (vMF on S²)
├── priors/                 # Bayesian prior construction & initialization
└── data_cleaning/          # Preprocessing pipeline
```

### Breaking Change Policy (Important)

- **No backward compatibility aliases.**
- All downstream code must import from explicit subpackage paths (e.g., `gimbal_pymc.hmm.engine`, `gimbal_pymc.cameras.triangulation`, etc.).
- Torch legacy support is removed; initialization is numpy-only.

### Implementation Summary (Completed)

- Created subpackages and moved modules.
- Updated internal imports throughout the codebase.
- Rewrote `gimbal_pymc/__init__.py` to export subpackages only (no convenience re-exports).
- Deleted deprecated / duplicate legacy modules and removed torch_legacy code paths.
- Standardized the Gamma helper on `gamma_mode_sd_to_shape_rate()`.

### Success Criteria (Revised to match implementation)

- All repository code (tests, examples, tools) uses explicit subpackage imports.
- P0 test gate passes (`pixi run test-p0`) and full suite passes (`pixi run test-all`) in CI/local.
- Documentation updated to reflect the new module layout and the breaking-change import policy.

### Deliverables

- Refactored package layout + updated imports.
- Updated README/docs to match new structure.
- Completion report with test evidence and migration mapping.

## P1. Anipose Processing & Prior-Inputs Pipeline

### Goal

Pass data to anipose (external to library) and process outputs to format usable by prior generation code (A1-3)

### Inputs

* `calibration.toml` (Anipose)
* triangulated 3D keypoints (per frame/joint), plus confidence if available
* optionally per-camera 2D detections and/or reprojection residuals
* subject metadata (species/strain, sex, age, weight/height)
* skeleton definition (joint names + parents)

### Outputs (canonical directory layout)

* `results/anipose_priors/camera_quality.json`
* `results/anipose_priors/segment_length_means.json`
* `results/anipose_priors/segment_length_sds.json`
* `results/anipose_priors/segment_length_quality.json`
* `results/anipose_priors/coverage.json`

### Contracts (schemas)

* Define JSON schemas with explicit units and parameterization.
* Define a joint-name mapping layer: Anipose names → GIMBAL indices.

### Implementation (proposed modules)

* `gimbal_pymc/anipose_io/ingest.py` (file reading + normalization)
* `gimbal_pymc/anipose_io/stats.py` (length stats, coverage, quality metrics)
* `gimbal_pymc/anipose_io/schemas.py` (pydantic/dataclass schemas)
* `scripts/build_anipose_priors.py` (CLI entrypoint)

### Success criteria

* Deterministic pipeline output for a fixed input + config.
* Produces valid schema outputs and coverage summary.
* Provides segment length estimates within expected scale.

### Deliverables

* CLI script + docs: how to run it
* One example subject checked into a small test fixture or synthetic equivalent

## A1. Camera Priors from Anipose Calibration

### Goal

Use Anipose calibration to provide **informative camera priors** (not fixed constants) to reduce pathological posterior geometry.

### Dependencies

* P1 camera_means/scales/quality

### Scope

* Parameterize camera extrinsics robustly (axis-angle or quaternion + translation).

* Intrinsics: focal length, principal point, distortion (as supported by current model).

* Prior widths derived from:
  
  * calibration residuals (preferred), or
  * conservative defaults if residuals unavailable.

### Implementation

* `gimbal_pymc/cameras/priors.py` (or `gimbal_pymc/priors/cameras.py`)
  
  * `build_camera_priors(anipose_camera_bundle, model_paramization) -> priors`

* Integrate into `build_camera_observation_model(...)` (now in `gimbal_pymc.cameras.observation_model`) via flags:
  
  * `use_camera_priors: bool`
  * `camera_prior_source: {"anipose", "user", "fixed"}`

### Success criteria

* Reduces divergences on a selected diagnostic rung compared to baseline.

## A2. Segment Length Priors

### Goal

Replace weak length priors with **data-informed** and **biologically plausible** priors to reduce redundancy among root/directions/lengths.

### Dependencies

* P1 segment_length_means/sds + subject metadata

### Scope

Multiple possible sources of priors

1. **Anipose-derived segment priors**
* Use segment length distributions computed from triangulated 3D.
* Make uncertainty depend on coverage/quality (coverage-conditioned SD).
2. **Population priors using subject characteristics**
* Provide mechanism for user specification of known bone lengths and uncertainties
* Allow both fixed and functional options

    Potentially: Combination of prior information

- Blending by Bayesian combination of uncertainty
3. Create a simple mapping from subject metadata to expected segment lengths.
* Keep “soft tissue / landmark jitter” flexibility but constrain it.
* Decide default CV for `rho` and `sigma2` (move away from 100% CV).

### Implementation

* `gimbal_pymc/priors/segment_lengths.py`
  
  * `build_segment_length_priors(stats, population_model, config)`

* `gimbal_pymc/priors/population.py`
  
  * population mean/variance functions (pluggable)

### Success criteria

* Demonstrable divergence reduction without fixing lengths.
* Reasonable posterior length estimates on synthetic and/or Anipose-initialized data.

## A3. Joint Anchoring to fixed point or sequence

### Goal

Support optional anchoring of one or more joints to external high-quality 3D data or to a known fixed point in the world.

Appropriate for:

- Fixed feet

- Using hips as reference and ignoring movement through space

- Anchoring hands to known position such as manipulandum or hand controllers

### Dependencies

* Needs to work properly with other sources of truth such as P1 based anipose data

### Scope

* Allow specifying an anchor set: `{joint_indices}` or joint names.

* Anchors can be:
  
  * per-frame time series (x[t,k,3])
  * fixed points

* Potentially: each anchor has sigma (global per joint, or per frame).

### Implementation

* Two possibilities:
  
  * Simply merged with positional priors such as those genreated by anipose
  
  * Change model to allow joints as data instead of parameters

* Potentially: Allow for potential missing data

### ### Success criteria

* Anchoring joints works without breaking shapes/gradients.

## C1. Capability Ladder Benchmarks

### Goal

Create a shared, reproducible benchmark ladder to track “how far we can go” under combined complexity.

### Scope

* Define **8 combined steps** increasing complexity across:
  
  * **joints, topology, camera coverage, noise/occlusions/outliers, sequence length**
  * Ensure datasets are long enough and rich enough to make identificaiton feasible

* Separate “very long T” scaling into a distinct temporal ladder.

### Implementation

* `datasets/ladder/step01.yaml` … `step08.yaml`

* `notebook/run_ladder.ipynb`
  
  * runs specified step + inference method
  * outputs standardized results JSON + brief markdown summary

* Output directory:
  
  * `diagnosis/results/<date>/<step>/<method>/...`

### Metrics (minimum)

* Divergences, treedepth hits
* Runtime
* Basic posterior sanity checks
* For synthetic: recovery metrics (if available)

### Success criteria

* Ladder runner works end-to-end.
* Establish baseline results for v0.2.1 tag.
* Used as acceptance gate for A1/A2/A3.
